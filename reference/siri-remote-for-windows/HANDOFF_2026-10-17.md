# Siri Remote for Windows — 인수인계 (2026-10-17)

## A. 사용자가 실제로 원하는 완성품

Apple TV Siri Remote 3세대 **A2854**를 **Windows Bluetooth 기반 PC 마우스/미디어 리모컨**으로 실사용한다. 터치패드는 커서 이동, 하드웨어 버튼은 클릭/뒤로/방향키/재생·음량 등으로 매핑한다. 최종 사용 시 WSL2, USB/IP, BlueZ, Linux 서버, 수동 콘솔이 필요 없어야 한다. 자동 재연결·트레이 앱은 후순위.

**원본 Linux 기능을 포크에서 유지할 필요는 없음.** 순수 Rust HID 디코더와 프로토콜 관련 테스트·저작권 고지는 재사용하고, BlueZ/D-Bus/PipeWire/uinput 등은 역사적 참고 구현으로 취급할 것. 소스 정리는 Windows 접근 가능성 검증 이후 실시.

## B. 검증된 사항 vs. 아직 가설인 사항

| 분류 | 관측 또는 가설 |
| --- | --- |
| **실기기 확인** | Intel AX200(USB ID `8087:0029`)을 WSL2 Ubuntu 22.04에 전달하고 Siri Remote BLE 발견·페어링 성공 |
| **실기기 확인** | `bluetoothctl info`에 `Paired: yes` / `Trusted: yes` / `Connected: yes`; 당시 배터리 99% |
| **실기기 확인** | 초기 BlueZ는 HID 서비스 `0x1812`를 숨겼지만 `--noplugin=input,hog` 적용 후 6 services/20 characteristics/6 descriptors로 정상 열거 |
| **실기기 확인** | `0xFB` 버튼, `0xFC` 터치 위치/호버/접촉 타원/압력 관련 수치·release 이벤트 실시간 수신 |
| **부분 확인** | `0xFA`는 보고서 목록에 있었으나 마이크 녹음/Opus 복호화는 실험으로 검증하지 않음 |
| **미확인** | Windows 내장 Bluetooth로 HID 입력 보고서를 읽을 수 있는지, WinRT GATT의 HID Report 특성 접근이 가능한지 |
| **미구현** | Windows 실행 파일, native 페어링/입력 주입, 자동 재연결, 트레이/설치 프로그램 |
| **별도 초안** | WSL→Windows 브리지 샘플은 프로토타입이며 Windows-native 제품이 아님; 실기기 실사용 검증되지 않음 |

## C. 실제 Linux 실험 경과 — 재현 가능한 핵심

1. Windows 관리자 PowerShell에서 `usbipd bind --force --busid 1-3` → `usbipd attach --wsl --busid 1-3`로 AX200 Bluetooth를 WSL2에 임시 연결. **버스 ID 1-3은 특정 PC에서 관측한 값**으로 범용값이 아니다.
2. Ubuntu 22.04 + BlueZ 5.64 + Rust 1.99.1. WSL에서 `lsusb` 및 `bluetoothctl list`로 어댑터 확인, BLE 스캔으로 실제 A2854 후보 확인.
3. 원본 Rust 빌드는 `libspa 0.9.2`와 Ubuntu 22.04의 PipeWire SPA 헤더 필드/타입 불일치로 실패. **로컬 실험에서만** `Cargo.toml`에서 `opus`, `pipewire`, `libspa` 제거, `src/main.rs`의 `mod mic;` 및 `mod audio;` 제거, Mic 실행 분기를 disabled error로 바꾸고 `cargo build --release -j 2` 성공. 원본은 `.bak-wsl`로 보관. **이 로컬 패치는 포크 저장소에 반영되지 않음.**
4. `./target/release/siri-remote pair --scan-seconds 8 --hold-seconds 10` 호출 시 “Connected and paired” 다음 bonded 판정 오류 발생. 그러나 별도 `bluetoothctl info`는 확실히 `Paired: yes`를 보여 줌. 당시 메시지는 실제 실패의 증거가 아니며 원인은 확정되지 않음.
5. 처음 `events`는 `input-hog profile accept failed`와 함께 GATT `0x1812`가 없어서 재연결 반복. WSL Bluetooth systemd override에 `ExecStart=/usr/lib/bluetooth/bluetoothd --noplugin=input,hog` 적용하고 재시작한 뒤 HID 서비스가 나타남.
6. `0x60,0xFA,0xFB,0xFC,0xFD,0xFE` 입력 보고서, `0xF0,0xF1` feature 보고서 열거. `0xF0`에 enable byte `0xAF` 전송. `0xF1`에는 ATT `0x82` 오류가 있었지만 입력 스트림은 정상 동작.
7. Right, Down, TV, Back, Play/Pause, Mute, Volume Up/Down의 press/release와 손가락 좌표·angle·major/minor·hover·pressure를 실제 로그에서 관찰. `view` 대시보드의 성공적 구동은 제출 로그로 별도 확인되지 않음.

**해석 주의:** `hover=true`에서도 `pressure=1` 또는 더 큰 값이 관측된다. pressure는 물리적인 뉴턴(N) 단위 힘이 아니며, 2D 좌표/hover만으로 실제 표면에서 몇 mm 떨어졌는지는 알 수 없다. 정확한 3D 추적을 주장하지 말 것.

## D. 현재 GitHub 소스의 상태 (2026-10-17)

`main`의 실행 코드는 여전히 Linux upstream 포크다. `Cargo.toml`은 `opus`/`pipewire`/`libspa` 의존성을 유지하고, `src/bluez` 및 `src/gamepad` 등이 남아 있다. 문서화 작업은 원본 실행 코드와 기존 라이선스를 수정하지 않는다.

참고할 주요 경로:
- `src/decoder.rs`: 버튼·터치 등 프로토콜 해석의 재사용 후보
- `src/session.rs`, `src/hid.rs`, `src/bluez/hid.rs`: Linux GATT/HID 특성 설정 및 알림 방식 참고
- `src/cli.rs`: 원본 CLI 명령 정의(Windows 제품 API 아님)
- `src/view/`, `src/gamepad/`, `src/audio/`: Linux 기반 기능 참고(Windows 제품 필수 구성 아님)
- `docs/windows-port/`: 날짜가 기록된 계획, 실험, 프로토콜 분석 및 검증 체크리스트

## E. 재개할 때 가장 먼저 실행할 검증

1. Windows Bluetooth 복구 여부 확인. **실험 종료 시 사용자 본인**이 관리자 PowerShell에서 다음 실행 (버스 ID는 환경에 따라 재확인):
   ```powershell
   usbipd detach --busid 1-3
   usbipd unbind --busid 1-3
   usbipd list
   ```
   이 문서가 해당 명령을 사용자 PC에서 실행했다는 뜻은 아니다.
2. Windows 기본 Bluetooth UI에서 A2854 페어링 시도. 페어링 성공 여부만으로 HID 데이터 접근을 주장하지 않는다.
3. Windows HID device-interface enumeration을 통해 실제 **report 0xFB/0xFC 읽기 가능**한지 실기기 검증. 불가하면 WinRT GATT 서비스/Report Reference/StartNotify/Feature 쓰기 가능성을 따로 확인.
4. 성공한 경로에 맞춰 Rust 순수 decoder를 분리하고 [실제 패킷 예제](docs/windows-port/OBSERVED_REPORT_FIXTURES.md)를 자동 테스트로 이관.
5. Win32 `SendInput`에 커서·클릭·키보드·미디어 제어 연결; 재연결과 가상 입력 해제, 일시정지 기능 검증.
6. 앱 자동 실행·트레이·배포는 그 후에. Windows 접근이 봉쇄된다면 먼저 정확한 오류/OS 버전/드라이버 상태를 문서화하고 재설계 판단.

**안전·저작권:** GPL-3.0 유지, upstream 저작권 표시, 리모컨 MAC/시리얼/사용자 식별 광고 바이트·원시 오디오를 공개 저장소에 올리지 않을 것. Windows 드라이버 보호 우회나 기본 마이크 녹음 기능을 전제로 설계하지 않는다.
