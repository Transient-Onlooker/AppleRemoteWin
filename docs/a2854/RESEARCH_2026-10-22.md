## Cross-checked standards and their implications

1. **Apple model / pairing procedure.** Apple's [A2854 product specification](https://support.apple.com/ko-kr/111844) names the **3rd-generation USB-C Siri Remote, model A2854** and Bluetooth **5.0**. Apple's [official pairing guidance](https://support.apple.com/ko-kr/102569) uses **Back + Volume Up for about five seconds**; this is a pairing action, **not a guarantee of Windows interoperability**, and could affect existing Apple TV pairing. Do not initiate it on the owner's behalf while the owner is away.

2. **Bluetooth USB command recipient.** [Bluetooth SIG USB transport specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-62/out/en/host-controller-interface/usb-transport-layer.html), Part B 2.2: HCI EP0 request \`0x20\` is the standard class/**device** form for a single-function controller; \`0x21\` is class/**interface** for a composite/controller interface. The measured Barrot \`33FA:0001\` succeeds with \`0x21\`. Keep the empirically verified VID/PID-specific rule and do not force \`0x21\` on unrelated adapters.

3. **Critical LE completion mask review.** The [LE event mask bit table](https://www.st.com/resource/en/application_note/an5270-stm32wb-bluetooth-low-energy-wireless-interface-stmicroelectronics.pdf), [BlueZ decoding](https://kernel.googlesource.com/pub/scm/bluetooth/bluez/%2B/7cb83c3c0ba19a9daba99a3b3f0b895a64c69572/monitor/packet.c) and [Linux controller initialization](https://android.googlesource.com/kernel/common/%2B/android-mainline/net/bluetooth/hci_sync.c) identify bit **9 (\`0x0200\`)** as **LE Enhanced Connection Complete** and bit **12 (\`0x1000\`)** as **LE Extended Advertising Report**. The fork previously sent LE event mask \`0x101F\`, leaving bit 9 off while the controller supported extended commands. The source now uses **\`0x121F\`**. This removes a plausible source of missing enhanced link-completion events; a standards-compliant controller may have returned the legacy completion under the old mask, so **the old mask is not proved to have caused any actual failure**. The existing Bluetooth 5 fake-HCI test now delivers the **enhanced** completion event instead of a legacy one.

4. **Advertising identity is not the same as authentication.** A public or random advertiser address must be passed with the correct HCI address type. The existing \`--connect-only\` does this while redacting addresses. The A2854 manufacturer prefixes are format fingerprints, and other Apple HID devices can share Apple company ID/HID UUID. The A2854 **bond-capable** path now requires \`A2854Advertisement.Classify(...).StrongCandidate\` rather than the older generic Apple+HID predicate; the gen-1 path remains unchanged.

5. **Pairing cryptography.** Bluetooth SIG's [Security Manager spec](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host/security-manager-specification.html) Part H 2.2.3–2.2.4 gives independent c1 and s1 official example vectors. These vectors **already existed** in \`tests/AppleRemote.Tests/SmpTests.cs\`, and their result was independently recalculated using standard AES-ECB on reversed wire-format bytes. They match the constants in the existing tests. This supports **legacy c1/s1 arithmetic**, **not** proof that the physical A2854 accepts the custom legacy SMP protocol or that its bond survives a rotating BLE address. Modern LE Secure Connections/ECDH would need a separate implementation if negotiated; do not assume it is present or absent solely from Bluetooth 5.0 capability.

## When the user has the physical remote again

1. Fetch the latest \`feat/a2854-support\`, preserve known-good binaries, run Release tests and the probe build, and check external Barrot still WinUSB/Started and internal Intel still BTHUSB/Started.
2. Run **only** \`dotnet run -c Release --project tools/A2854.Probe/A2854.Probe.csproj -- --usb 33FA:0001 --connect-only --seconds 30\`. Once **Starting scan** appears, wake A2854; if necessary use Apple's **Back + Volume Up ~5 seconds** while near the USB adapter. No need to log any BLE address.
3. Interpret results by stage, not by assumption:
   - **Scan timeout:** remote did not provide the expected strong advertisement in that window; no link attempt occurred.
   - **LE Create Connection rejected / status nonzero:** log only HCI opcode, status, connection stage and whether legacy/extended command was selected.
   - **LE initiation accepted but completion timed out:** investigate event mask \`0x121F\`, public/random peer address type, address rotation/freshness, and connection-cancel/cleanup ordering. Do not immediately blame pairing or HID.
   - **LE Connection Complete succeeded but Disconnect failed:** external-controller-only cleanup; report both error and cleanup outcome. No bond state should have changed.
   - **LE Connection Complete + Disconnection Complete succeeded:** record **link-only success**. Do not claim pairing/GATT/HID success.
4. Only after a clean link-only result, design a **separately authorized** SMP/encryption step with cancellation, error diagnostics, and local-only bond-key persistence. After that validate GATT Report Reference \`0x2908\`, Feature Report \`0xF0 <- 0xAF\`, input report \`0xFB\` (buttons), \`0xFC\` (touch); exclude mic \`0xFA\`.

### Remaining risks to resolve after LE link success

- **BLE privacy/bond continuity:** a rotating temporary address may need identity resolution/IRK, not merely reuse of an LTK keyed by the latest temporary address. Existing single-bond reuse is experimental.
- **Security protocol negotiation:** mock-device Just Works success does not imply a physical A2854 supports the same legacy SMP handshake. Preserve precise status responses and avoid automatically deleting existing keys on unexplained failures.
- **Cancellation / late completion:** a connection completion after a local timeout could leave a link until the dedicated external controller's cleanup Reset. Never reset or rebind the internal Intel Bluetooth adapter.
- **Device identity:** prefixes and human proximity are not cryptographic identity verification; maintain an operator confirmation before *first bonding*.
- **Driver trust lifecycle:** self-signed machine-wide trust is temporary operational scaffolding, not a recommended production driver-distribution model.

## 2026-10-22 follow-up: connection cancellation audit and local Release verification

The local Windows checkout was fast-forwarded to `cc129a31a44c2a31c8d440edffc553239fa34310`. A writable temporary source copy was used because the checkout's `obj` directories are not writable. The latest source plus the cancellation fixes below passed **109/109 Release tests**; the full solution Release build and standalone A2854.Probe Release build both completed with **0 errors**. NuGet vulnerability metadata could not be reached (`NU1900`); the full solution build also reported non-fatal app post-build download warnings for unrelated driver/firmware artifacts. No driver/certificate operation or hardware connection test was run.

The cancellation review found and fixed races in `LeCentral.ConnectAsync`: cancellation used to fire-and-forget `LE Create Connection Cancel`, allowing cleanup to overtake it; and a late successful Connection Complete could be abandoned without disconnecting the new handle. Cancellation now awaits the cancel command response, drains the matching completion, disconnects a late successful handle and waits for its Disconnection Complete. One concurrent create attempt per `LeCentral` is enforced. Cancel responses `Unknown Connection Identifier (0x02)` and `Command Disallowed (0x0C)` are treated as race signals and the final create event is drained. Failed LE Connection Complete events are accepted with only subevent+status, while truncated successful events are rejected. Regression coverage includes both cancel-race status values and late success cleanup.

Protocol comparison: Bluetooth SIG Core HCI defines LE Extended Create Connection as an initiating-PHY bitmap followed by a 16-octet parameter block per selected PHY; the one-PHY 1M command assembled here is 26 parameter octets (filter policy, own address type, peer address type/address, PHY mask, scan interval/window, and 12-byte connection timing block). The controller first reports command acceptance/rejection through Command Status; the later legacy or Enhanced Connection Complete meta-event reports connection status and handle. The implementation recognizes both event subevents, enables bit 9 in LE event mask `0x121F`, and uses the handle from successful completion. Public/random address types are preserved; Extended Advertising public/random identity types are normalized to their underlying public/random classes because this path uses the reported address as the peer address. A rotating private address can still become stale between scan and connect; this path has no IRK-based identity resolution. LE Create Connection Cancel applies to both legacy and extended initiation. The Bluetooth SIG spec requires a final completion event for a cancelled create procedure; if it is missing, the probe's finally block resets only its dedicated external Barrot controller. No actual controller connection has yet exercised these semantics.

SMP/GATT readiness remains unproven. Existing `SmpPairing` implements legacy Just Works confirm/random exchange (`c1`), STK derivation (`s1`), encryption, then remote LTK and Master Identification reception; official c1/s1 vectors pass. It does not implement LE Secure Connections/ECDH key generation and f4/f5/f6/g2, or IRK/identity-key distribution and address resolution. The bond store is keyed by observed address; single-bond fallback across a fresh random address is an experimental heuristic, not identity proof. After encryption, HID GATT discovery looks for service `0x1812`, Report `0x2A4D`, Report Reference `0x2908`, and writes Feature Report `0xF0` value `0xAF`; the diagnostic allowlist retains button `0xFB` and touch `0xFC`, excluding microphone `0xFA`. The mock validates protocol plumbing and selected legacy pairing behavior but uses synthetic services/reports and does not establish the A2854's real SMP mode, report map, rotating-address bond continuity, or physical input compatibility.

The `--connect-only` mode remains isolated before the normal secure/GATT workflow and constructs `LeCentral(respondToSignaling: false)`; it performs scan, create and disconnect only. Once the remote is physically available, the next test is:

`dotnet run -c Release --project tools/A2854.Probe/A2854.Probe.csproj -- --usb 33FA:0001 --connect-only --seconds 30`

Software is verified only. Existing hardware evidence remains Windows-native HCI Reset, Read Local Version, BLE scan and 95 strong advertisement-format candidates on the external Barrot. LE Create Connection, Connection Complete, Disconnect, SMP, GATT and HID reports remain unverified on the real A2854.
