# A2854 — passive WPF GUI smoke-test gate

**Source written on 2026-10-23.** This is a safety correction discovered after the independent Windows verifier reported three consecutive **256/256** Release-test passes at `302fdb1`, a focused **99/99** subset, full Release/WPF/Probe builds with zero warnings/errors, and no physical A2854 activity. The old intermittent gen-1 random-address test did not fail in these three runs (observed ~250ms, 48ms, 102ms). Those results predate this new GUI-startup guard and must not be counted as its validation.

## Why this gate is necessary

The pre-change existing WPF application did `MainWindow.Window_Loaded() -> MainViewModel.Start() -> RemoteViewModel.Start() -> StartSession()` unconditionally. If `A2854Mode` was persisted from a previous session, simply opening the GUI could open the Barrot HCI, establish encrypted BLE reconnection and issue CCCD writes and `0xF0 <- 0xAF` without the operator pressing Start. The device-change timer could likewise automatically restart a connected A2854 session in some cases. This is inappropriate when a separate operator approval is required for hardware GATT writes.

## Source correction (not yet built on local Windows)

- `RemoteStartupPolicy.AutoStartSession(true) == false`: persisted A2854 skips startup transport initialization. **Even when A2854 mode is OFF**, if a dedicated Barrot `33FA:0001` is detected through read-only PnP interface enumeration, initial auto-start is also skipped to prevent the legacy driver from taking the dedicated adapter. First-gen auto-start remains unchanged **when no dedicated Barrot is present**.
- `RemoteViewModel.Start()` still starts existing WPF UI timers, but when A2854 is selected **or Barrot is detected**, it does not StartSession or start the Windows BLE scanner. If device-interface enumeration fails, it fails closed (requires manual Start) rather than guessing.
- `UsbHci.OpenForLegacyRemote` is used by the existing first-generation `RemoteSession` path and excludes dedicated `33FA:0001` from explicit selection and WinUSB auto-fallback, including when a previously saved adapter was removed. Other legacy controllers remain eligible. Dedicated A2854 mode still uses only `UsbHci.OpenForUsbId(33FA:0001)`.
- Manually starting a legacy session after passive launch is still supported and can resume the ordinary Windows BLE scanner when an appropriate legacy adapter is present.
- `SettingsViewModel.OnA2854ModeChanged()` now stops WinRT BLE scanner on switching to A2854; switching back to 1st gen resumes scanner without starting a new session.
- `RemoteStartupPolicy.AllowBackgroundRestart(true) == false`: automatic ESP32 takeover, PnP adapter-change restarts and the Debug pairing callback cannot implicitly start/restart an A2854 link. Existing 1st-gen behavior remains unchanged when the flag is false.
- `RemoteViewModel.PairDevice()` rejects Windows Bluetooth pairing while A2854 is selected, even when no WinUSB adapter has yet been opened.
- New `RemoteStartupPolicyTests` verify persisted A2854/manual-Start behavior, legacy-with-Barrot safeguards, and unchanged legacy auto-start without Barrot. `UsbHciTransportQuirksTests` validates dedicated-Barrot PnP classifier with Intel/gen-1/other-Barrot negative cases.

The app still **requires a separate deliberate Start button click** for an A2854 session; that action may use an already stored CurrentUser DPAPI LTK and send ATT writes. It must not be part of a GUI-only smoke test. A2854 mouse/keyboard injection also stays separately opt-in. Existing USB/Bluetooth drivers, bond files, internal Intel AX200 and authentication certificates are unchanged.

## Additional static safety audit

The main-author audit found three ways to bypass the deliberate A2854 Start gate: restarting after a successful driver operation, reusing first-generation Pair/Forget commands, and completing an in-flight Windows pairing after switching modes. `RemoteStartupPolicy` now blocks the legacy commands and the implicit restart in A2854 mode, and the async pairing callback rechecks the current mode before restarting anything. The Windows BLE scanner stays stopped if mode changes during pairing. First-generation commands retain their existing behavior. Fresh Windows Release tests and runtime verification remain pending; no A2854 hardware or OS input was exercised by this source edit.

### Remaining unverified

WPF runtime data bindings, passive GUI launch, physical GUI encrypted reconnection, Windows SendInput mouse input, long-duration BLE stability, and cross-process Barrot USB exclusive access. The original real 8-second `A2854.Probe` observation (33 0xFB + 360 0xFC frames; successful CCCD disable and host 0x16) remains the physical HID baseline, not a test of GUI auto-start.

## 2026-10-23 verification follow-up — native open cleanup

The reviewer found no remaining implicit A2854 start bypass, but reported one pre-existing static defect: if WinUSB initialization/interface validation succeeded and `UsbHci` construction failed in `FindPipes` or later initialization, `TryOpenAdapter` skipped `WinUsb_Free` and the file-handle disposal. The main agent now uses a `try/finally` with ownership transfer only after successful construction, and stops any first reader if starting the second reader fails. ## 2026-10-23 — follow-up reader lifetime hardening (pending Windows verification)

Windows verifier at `30af5645`: 272/272 Release tests passed three times and all Release builds were warning/error-free. Its external 16-scenario harness nevertheless reproduced freeing WinUSB while readers were still alive after Abort/Join failure, incomplete Dispose on an exception, and masking the initial constructor exception on cleanup errors; concurrent Dispose was flagged by static review. The main author separated passive construction from reader start, transferred handle ownership before launching threads, added `UsbReaderShutdown` (portable mock-regression tests), and made native release occur **only after both reader threads have exited**. Dispose is bounded and idempotent; pending cleanup retains handles and remains observable via `CleanupCompletion`, awaited by the WPF driver task and A2854.Probe. Incomplete or faulted A2854 cleanup blocks a subsequent Start. If a native read never exits, handle release may remain pending indefinitely rather than free a live handle. Normal native cleanup failures are surfaced through completion. Native rollback cleanup exceptions are logged without replacing a preceding constructor exception. **This new source has not been independently Windows-built/tested.** No GUI, live USB, BLE, GATT, bond change or input injection was executed.
